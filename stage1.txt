# 🛡️ Global Security, Roles & Authentication (Phase 1)

### Feature: Participant Registration
*   **Test Case 1 (Positive):** Register a new **IIIT Student** with an `@students.iiit.ac.in` email.
    *   **Expected Result:** Successful registration, redirects to dashboard, profile shows `Participant Type: IIIT Student`.
*   **Test Case 2 (Positive):** Register a new **Prof/Staff** with an `@iiit.ac.in` email.
    *   **Expected Result:** Successful registration, profile shows `Participant Type: IIIT Professor`.
*   **Test Case 3 (Positive):** Register an **Outside Participant** with a Gmail/Yahoo email.
    *   **Expected Result:** Successful registration, profile shows `Participant Type: Outside IIIT`.
*   **Test Case 4 (Negative):** Attempt to register with an already existing email.
    *   **Expected Result:** `400 Bad Request` with message "User already exists".
*   **Test Case 5 (Negative):** Attempt to register via the API with `role: "admin"`.
    *   **Expected Result:** Registration blocked; `403 Forbidden` "Admin registration is restricted".
*   **Test Case 6 (Negative):** Attempt to register via the frontend/API with `role: "organizer"`.
    *   **Expected Result:** Registration blocked; `403 Forbidden` "Organizer self-registration is not allowed."

### Feature: Role-Based Access Control (RBAC) & Routing
*   **Test Case 7 (Negative - Participant):** As a logged-in Participant, attempt to manually navigate to `/admin`, `/events/create`, or `/scanner` in the URL bar.
    *   **Expected Result:** Redirected to Dashboard or 403 Access Denied.
*   **Test Case 8 (Negative - Organizer):** As a logged-in Organizer, attempt to navigate to `/admin` or `/my-registrations`.
    *   **Expected Result:** Redirected or blocked.
*   **Test Case 9 (Negative - Unauthenticated):** In an incognito window, attempt to access `/dashboard` or `/profile`.
    *   **Expected Result:** Redirected immediately to `/login`.

### Feature: Session Management & Logout
*   **Test Case 10 (Positive):** Log in, close the browser tab, and reopen the application in a new tab.
    *   **Expected Result:** User remains logged in (JWT persists in localStorage).
*   **Test Case 11 (Positive):** Click the "Logout" button.
    *   **Expected Result:** JWT token is cleared from localStorage, user is redirected to `/login`. Clicking the browser "Back" button should not allow access to protected routes.

# 🚀 Phase 2: User Onboarding & Events Foundation

### Feature: Participant Onboarding Flow
*   **Test Case 12 (Positive):** New participant logs in for the first time.
    *   **Expected Result:** Redirected to the Onboarding screen (`/onboarding`).
*   **Test Case 13 (Positive):** Select "Areas of Interest" and "Clubs to Follow", then save.
    *   **Expected Result:** Preferences saved to DB. User is navigated to `/dashboard`.
*   **Test Case 14 (Edge Case):** Click "Skip Onboarding".
    *   **Expected Result:** User proceeds to Dashboard. The Profile page should display a mechanism/prompt indicating incomplete profile.

### Feature: Event Validation & Data Integrity
*   **Test Case 15 (Negative):** As an organizer, create an event with a negative registration fee, negative registration limit, or negative stock.
    *   **Expected Result:** Backend Mongoose validation blocks the request (`min: 0` constraints).
*   **Test Case 16 (Negative):** Create an event where `endDate` is before `startDate`, or `registrationDeadline` is after `endDate`.
    *   **Expected Result:** Form validation should catch this and prevent submission.

# 🏗️ Phase 3: Core Features & Workflows

## 3.1 Organizer Capabilities

### Feature: Event Creation (Draft → Published Workflow)
*   **Test Case 17 (Positive):** Create a new "Normal" event and save it as "Draft".
    *   **Expected Result:** Event appears in Organizer Dashboard as Draft. It does **not** appear on the public Browse Events page.
*   **Test Case 18 (Positive):** Edit the Draft, add a Custom Form (short answer, MCQ), and change status to "Published".
    *   **Expected Result:** Event is live. Searchable on the Participant Browse Events page.
*   **Test Case 19 (Negative):** Attempt to edit the Custom Form structure *after* the first participant has registered.
    *   **Expected Result:** Form Builder is locked/disabled. Cannot add or remove questions.
*   **Test Case 20 (Negative):** Attempt to change the `status` of a Completed event back to Draft.
    *   **Expected Result:** State transition blocked by backend logic.

### Feature: Organizer Dashboard Analytics
*   **Test Case 21 (Data Integrity):** Verify that the "Total Revenue" and "Registration Count" cards accurately match the sum of *Confirmed/Successful* registrations only (ignoring Pending/Cancelled).

## 3.2 Participant Capabilities

### Feature: Browse Events & Filters
*   **Test Case 22 (Positive):** Search for an event using a partial keyword (e.g., "Hack" for "Hackathon").
    *   **Expected Result:** Fuzzy/partial search returns the correct event.
*   **Test Case 23 (Positive - Followed Filter):** Toggle the "Followed Clubs" filter.
    *   **Expected Result:** Only displays events created by organizers the participant is following.
*   **Test Case 24 (Integrated):** Combine "Followed Clubs" + "Date Range" + "Search Text".
    *   **Expected Result:** All parameters apply conjunctively.

### Feature: Normal Registration & Custom Forms
*   **Test Case 25 (Data Integrity):** Register for a Normal event and fill out the custom form. Enter >50 words in a "Short Answer" field.
    *   **Expected Result:** Form submission blocked by the newly implemented 50-word guard clause.
*   **Test Case 26 (Concurrency/Edge Case):** Set an event limit to `1`. Have two accounts attempt to hit the "Register" API simultaneously.
    *   **Expected Result:** The atomic lock ensures only 1 succeeds; the other gets a "Registration Limit Reached" error.
*   **Test Case 27 (Positive):** Successfully register.
    *   **Expected Result:** Confirmation email sent with PDF ticket (QR code). Registration appears in "My Events".

### Feature: Public Organizer Directory
*   **Test Case 28 (Positive):** Navigate to Clubs/Organizers. Click "View Events" on a club card.
    *   **Expected Result:** Navigates to `/organizers/:id`. Shows Club Name, Contact, Follower Count, and distinct grids for Upcoming vs. Past/Ongoing events.

## 3.3 Admin Capabilities
*   **Test Case 29 (Positive):** Log in as Admin. Create a new Club Organizer account.
    *   **Expected Result:** Password/Email generated. Account immediately usable to log in.
*   **Test Case 30 (Positive):** Delete or ban an Organizer.
    *   **Expected Result:** The Organizer is immediately kicked out, and their events are removed/hidden from the public feeds.

# 👕 Phase 4: Merchandise & Attendance (Tier A)

### Feature: Merchandise Payment Workflow
*   **Test Case 31 (Positive):** Participant registers for a Merchandise Event.
    *   **Expected Result:** Registration created with status `pending`. Stock is **NOT** decremented yet. No QR ticket sent.
*   **Test Case 32 (Positive):** Participant uploads Payment Proof (Image via Cloudinary).
    *   **Expected Result:** Organizer can view the receipt in their Dashboard.
*   **Test Case 33 (Positive):** Organizer clicks "Approve" on the payment.
    *   **Expected Result:** Status changes to `confirmed`. Event Stock is atomically decremented by 1. PDF Ticket with QR is instantly emailed to the user.
*   **Test Case 34 (Negative - Hoarding):** Set stock to 1. User A orders but does not pay (Pending). User B orders and Organizer approves User B first. Stock becomes 0. Organizer attempts to approve User A.
    *   **Expected Result:** Approval fails; "Out of Stock" error. User A's order must be rejected.
*   **Test Case 35 (Negative):** Participant attempts to cancel a `confirmed` Merchandise purchase.
    *   **Expected Result:** Cancellation disabled/blocked for physical goods.

### Feature: QR Scanner & Attendance Tracking
*   **Test Case 36 (Positive):** Organizer uses the `/scanner` page to scan a participant's QR code (or enters the Ticket ID manually).
    *   **Expected Result:** Participant's `attendanceStatus` is updated to `Present` with a timestamp.
*   **Test Case 37 (Negative):** Scan the exact same QR code a second time.
    *   **Expected Result:** UI shows "Duplicate Scan / Already Present" alert.
*   **Test Case 38 (Negative):** Attempt to cancel the registration of a user who has already been marked `Present`.
    *   **Expected Result:** Cancellation fails (attendance already locked).

# 💬 Phase 5: Forum & Admin Passwords (Tier B)

### Feature: Real-Time Discussion Forum
*   **Test Case 39 (Positive):** Participant A posts a question on the Event Forum. Participant B replies to it.
    *   **Expected Result:** Text appears instantly without refreshing the page (via Socket.IO). Participant A receives an offline notification.
*   **Test Case 40 (Negative):** An unregistered user attempts to view or post in the forum.
    *   **Expected Result:** Blocked; UI hides forum or API returns `403`.
*   **Test Case 41 (Positive - Organizer):** Organizer pins a message.
    *   **Expected Result:** Message floats to the top of the chat for all users.
*   **Test Case 42 (Positive - Notifications):** Participant logs in after receiving a reply.
    *   **Expected Result:** Navbar notification bell shows a red `1`. Clicking it opens the unread notification. Clicking the notification routes them to the specific event. 

### Feature: Organizer Password Reset Workflow
*   **Test Case 43 (Positive):** Organizer clicks "Forgot Password" on login screen and submits a reason.
    *   **Expected Result:** Request generated. Admin sees the request in the Admin Dashboard.
*   **Test Case 44 (Positive):** Admin approves the reset request.
    *   **Expected Result:** New random password generated, shown to Admin, and Organizer can successfully log in with it.

# 🕵️ Phase 6: Anonymous Feedback (Tier C)

### Feature: Anonymous Feedback Engine
*   **Test Case 45 (Positive):** A participant whose attendance is marked `Present` navigates to the Event Details and submits a 4-star rating with comments.
    *   **Expected Result:** Success message. The feedback UI disappears.
*   **Test Case 46 (Negative):** Participant attempts to submit feedback for an event they did *not* attend (attendance = `Absent/Pending`).
    *   **Expected Result:** Form is disabled or API returns `403 Feedback only for attended events`.
*   **Test Case 47 (Negative):** Participant attempts to submit feedback twice for the same event.
    *   **Expected Result:** Blocked by `registration.feedbackSubmitted` flag.
*   **Test Case 48 (Data Integrity / Privacy):** Organizer checks the Feedback Analytics in their dashboard.
    *   **Expected Result:** Organizer sees the aggregate average rating, distribution graph, and the text comment. The Organizer **cannot** see the name or email of the submitter anywhere in the UI or Network Payload.
